# テスト用テクスチャ

**TextureChannelPacker** の動作確認用サンプルテクスチャです。プラグインを有効にした任意の UE プロジェクトにインポートし、以下の手順で確認してください。

これらは [`generate_test_textures.py`](generate_test_textures.py) で生成されています（標準ライブラリのみ — Pillow や numpy は不要です）:

```
python3 generate_test_textures.py          # 標準セット
python3 generate_test_textures.py --huge   # 16K ストレステスト用テクスチャの再生成
```

## インポート設定

このツールはテクスチャの **Source**（インポートされた生ピクセル）を読み取るため、`sRGB` のインポート設定は**抽出される値に影響しません**（コンテンツブラウザ上での見え方が変わるだけです）。パック済みサンプルについては、インポート後に **Compression = Masks**、**sRGB = オフ** に設定しておくと、プレビューの見た目とツールが報告する値が一致します。

16bit のサンプルは精度を保つ必要があります。**Compression = Grayscale** のままにし、インポート時に 8bit へ変換されないようご注意ください。

| :--- | :--- | :--- | :--- |

| `T_UnpackTest_Uniform_ORM.png` | 256×256 | RGBA8 | 未使用チャンネル検出用。B は全面 0、A は全面 255。 |
| `T_UnpackTest_NonSquare_ORM.png` | 512×128 | RGBA8 | 非正方形時のプレビューグリッドと出力の確認。 |

| `T_TestMaterial_Roughness.png` | 256×256 | Gray8 | パック入力（Green / ラフネス）。**意図的に半分の解像度** — 自動リサイズの確認用。 |
| `T_TestMaterial_Metallic.png` | 512×512 | Gray8 | パック入力（Blue / メタリック）。エッジの立った円形マスク。 |

16K の2ファイルはパターンの圧縮効率が高いため、ディスク上では約15MB / 約4MB に収まっています。重要なのは展開後のソースデータ量の方です。

## 確認1 — アンパック

1. **Tools > Texture Channel Packer** を開き、**アンパック** タブに切り替えてプリセットを **ORM** にします。
2. `T_UnpackTest_ORM` を割り当てます。

選択した時点で（ボタン操作なしで）以下が表示されるはずです:

| セル | パターン | 出力名 |
| :--- | :--- | :--- |
| **R → AO** | 左右方向の滑らかなグラデーション | `T_UnpackTest_AO` |
| **G → Roughness** | エッジの立ったチェッカー模様 | `T_UnpackTest_Roughness` |
| **B → Metallic** | 滑らかな同心円リング | `T_UnpackTest_Metallic` |
| **A** | エッジの立った斜めストライプ | `T_UnpackTest_A` |

これによりチャンネルが入れ替わっていないこと、スマート命名が `_ORM` を除去したこと（`T_UnpackTest_ORM` → `T_UnpackTest`）、プリセットがチャンネル別サフィックスを供給していることを同時に確認できます。

**テクスチャをアンパック** を押すと、`Grayscale` 圧縮・`sRGB` オフ・512×512 の G8 アセットが4枚作成されます。

プリセットを **MRA** に切り替えると、セルのラベル（`R → Metallic`、`B → AO`）と出力名だけが変わり、画像自体は変化しないはずです。

## 確認2 — 未使用チャンネル検出

`T_UnpackTest_Uniform_ORM` を割り当てます。期待される結果:

- **R** と **G** には内容が表示され（ビネット / 縦グラデーション）、チェックは入ったままです。
- **B** は真っ黒で表示され、**均一 (0)** バッジが付き、自動的にチェックが外れます。
- **A** は真っ白で表示され、**均一 (255)** バッジが付き、自動的にチェックが外れます。

この状態で **テクスチャをアンパック** を押すと、生成されるのは2枚だけです。B のチェックを入れ直せばそのまま出力されます — バッジはあくまで補助であり、出力を禁止するものではありません。

## 確認3 — 非正方形

`T_UnpackTest_NonSquare_ORM`（4:1）を割り当てます。4つのプレビューセルが正方形に引き伸ばされず 4:1 を保つこと、抽出されたアセットが 512×128 になることを確認してください。

## 確認4 — パック

**パック** タブでプリセット **ORM** を選び、以下を割り当てます:

- Red ← `T_TestMaterial_AO`
- Green ← `T_TestMaterial_Roughness`（256×256）
- Blue ← `T_TestMaterial_Metallic`
- Alpha ← 空のまま

ファイル名が `T_TestMaterial_ORM` に自動入力されるはずです。解像度を 512×512 に設定して **プレビュー更新** を押すと、**表示** ドロップダウンで R にビネット、G にブロブ（256から拡大）、B に円、A に真っ白が表示されます。

生成すると、次の確認で使う往復テストの入力になります。

## 確認5 — 往復（ラウンドトリップ）

いま生成した `T_TestMaterial_ORM` をアンパックします。

- **R（AO）** と **B（Metallic）** は元画像と**ピクセル単位で完全一致**するはずです。どちらもネイティブの 512×512 のままパックされ、全工程が 8bit で再サンプリングが発生しないためです。
- **G（Roughness）** は一致しません。パック時に 256→512 へバイリニア補間で拡大されており、これは元に戻せないためです。
- **A** は **均一 (255)** バッジが付くはずです。空だったアルファスロットがパック時に白で埋められたためです。

## 確認6 — 16bit ソース

`T_TestMaterial_Height16` をパックの任意のスロットに割り当てます。真っ黒やバンディングだらけのノイズではなく滑らかな場として読み込まれれば、`TSF_G16` パスが 16bit → 8bit 変換を正しく行えています。

アンパックタブに入れてみるのも有用です。単一チャンネルのソースなので R/G/B すべてに同じ場が表示され、**A は 均一 (255) として報告されます**。

## 確認7 — 16K ストレステスト

`T_StressTest_16K_ORM`（RGBA8）と `T_StressTest_16K_Gray`（Gray8）を使用します。どちらも 16384×16384 で、ツールが受け付ける最大サイズです。

**先にお読みください。** これらは意図的に高負荷であり、コストの大半はプラグインではなくエディタ側のものです:

- 16K PNG のインポートには時間がかかり、RGBA の方はおよそ 1GB の RAM を要します。インポート自体が失敗する場合は、ツールではなく UE のインポータ側の問題です。
- 抽出される 16K チャンネルは1枚あたり 256MiB の `G8` アセットになります。`Grayscale` 圧縮は非圧縮の `PF_G8` なので、**ミップを含めて1枚あたり約 341MB のビデオメモリ**を消費します。4チャンネルすべてをアンパックすると GPU 上に約 1.4GB が乗ることになります。VRAM を意図的に追い込む目的でなければ、チェックは1〜2チャンネルに留めてください。
- 8192 を超える解像度では処理前にメモリ警告ダイアログが表示されます。これは正常な動作なので「はい」で続行してください。

各手順で確認すべき内容:

| 手順 | 期待される結果 |
| :--- | :--- |
| アンパックタブで `T_StressTest_16K_ORM` を選択 | 少し待つと 2×2 プレビューが表示され、**メモリがギガバイト単位で跳ね上がらない**こと（プレビューはソースをコピーせずストリーミング処理するため）。R=横グラデーション、G=16×16 チェッカー、B=縦グラデーション、A=真っ白（**均一 (255)** バッジが付きチェックが外れる）。 |
| 1チャンネルだけアンパック | エラーなく完了し、アセットは 16384×16384 になること。処理中も進捗ダイアログのキャンセルが効くこと。 |
| `T_StressTest_16K_Gray` を Red に入れて 16384×16384 でパック | メモリ警告の後、生成が完了すること。これが 16K のエンドツーエンド経路です。 |
| 生成中にキャンセル | 「キャンセルされました」のトーストが出て中断し、中途半端なアセットが残らないこと。 |

**このファイルでは確認できない項目.** サイズ超過の拒否パス（ソースが `INT32_MAX` バイトを超えた場合に、オーバーフローせず「テクスチャが大きすぎます」と明示的に拒否する動作）には 2GiB を超えるソースデータが必要です。16K では1ピクセルあたり8バイト以上（`RGBA16` で 2GiB、`RGBA32F` で 4GiB）が該当しますが、これは PNG では表現できず、リポジトリに含めるにも大きすぎます。確認したい場合は 16K の `RGBA32F` EXR をローカルで作成してください（ただし UE 側のインポータの方が先に限界を迎える可能性が高いです）。
